# 記憶建立與公平召回比較

本工具回答兩個不同問題：必要線索有沒有進入記錄，以及已記錄的線索能不能被找回。它不評分小說文筆，也不把找到較多章節直接解讀為寫作品質改善。

## 1. 先查記錄是否保留必要線索

在專案根目錄執行：

```bash
.venv/bin/python -m scripts.benchmark_memory
```

預設只讀 [虛構題組](../examples/memory-eval/cases.json)，不建立索引、不啟動模型、不呼叫 API、不存取既有小說。JSON 報告輸出到 stdout，不另外建立版本檔。

題組含 9 章、8 題、9 項必要證據，覆蓋早期暗語、別名連回交接、物品最新持有人、人物誤解與實際狀態、承諾條件，以及摘要漏掉的操作細節；另有相似線索與時間範圍以後的變更。

每章分開保存正文 `body`、實際摘要 `summary` 與完整章節記錄 `record`。每題的 `requirements` 是人工指定的必要證據，帶原文精確引文及檢查片語 `probes`。程式先確認引文在正文中、片語出自引文、來源章早於查詢時間，再分別檢查摘要與整筆記錄。

這是已核對虛構材料的精確片語覆蓋檢查，不是一般語意判讀器。真實小說的改寫、否定或指涉仍需人工核對，不能直接以字串未出現判定漏記。

## 2. 用相同文字比較兩套召回

現行正式流程中，Chroma 索引摘要欄位，Jev 同步整筆章節記錄。本工具不改那兩個入口；它在隔離的暫存目錄建立對照：

- 預設 `--corpus record`：兩邊都接收完全相同的整筆記錄。
- `--corpus summary`：兩邊都只接收同一摘要，作為記錄內容的另一組對照；不要與前一組混算。
- 同題使用相同問題、章號截止點、回傳章節上限與指定 embedding 模型名稱，記錄語料 SHA256。gold 引文、檢查片語及正文不送給後端。
- Chroma 保留章前組裝目前使用的距離上限 1.0；Jev 保留現有探索預算。相同 encoder 名稱不等於兩個套件的向量前處理完全一致，因此結果代表這兩個接法的對照，不是單一演算法變因的實驗。
- 比較單位是命中的來源章與該筆輸入記錄是否保有所需線索，不以 Jev 回傳的截短文字打分；兩邊回查相同本地題組。

實跑要使用已準備的兩套環境與已快取模型，並明確允許付費 API：

```bash
.venv/bin/python -m scripts.benchmark_memory --live --allow-paid-api \
  --encoder-model "$JEV_MEM_ENCODER" --jev-model "$JEV_MEM_MODEL"
```

先設定實際的 `JEV_MEM_ENCODER` 與固定版本的 `JEV_MEM_MODEL`；Jev 環境沿用 `JEV_MEM_PYTHON`、`JEV_MEM_SOURCE`、`TYPESAFE_API_KEY`。工具不讀鑰匙圈或憑證檔、不印密鑰、不安裝套件、不下載模型。缺少環境或本地依賴時先失敗，不把未執行當空命中。預設離線命令不需要這些環境設定。

## 3. 怎麼讀報告

同一批題目測試模型重用時，在上述 live 命令加 `--jev-worker session`；預設 `oneshot` 保留每題重啟的對照。session 的建庫仍獨立執行，第一個實際查詢才啟動查詢程序與 encoder，因此第一題是冷啟動，後續題目才是暖機。不要把第一題混成穩態延遲，也不要漏掉它的實際等待時間。工具會保留 `trace.timings` 與逐次 `trace.api_calls`；HTTP 計時是客戶端往返，不是服務端推論時間。

| 診斷 | 意義 | 優先檢查 |
|---|---|---|
| `capture_gap` | 必要片語存在正文，但不在本次輸入記錄 | 摘要／記錄是否保留了後續需要的內容 |
| `retrieval_miss` | 必要片語已在輸入記錄中，但成功查詢未回傳該來源章 | 查詢、候選與排名 |
| `retrieved` | 所需內容已記錄，且來源章被找回 | 再由寫作 Agent 核對原文與角色知情 |
| `not_evaluated` | 後端未跑、執行失敗、輸入不一致或輸出無效 | 先處理執行／比較條件，不算成召回失敗 |

`recall_on_captured` 只以已進入輸入記錄的必要證據為分母；若全部缺漏或查詢無效，值為 `null`，不是 0 或 100%。同時保留 `all_evidence_available` 與 `all_evidence_retrieved`，不能只報前者排除缺漏後的好看分數。未來章、未知章、重複章或超過回傳上限都屬無效輸出。

`comparison_ready: true` 只表示兩套實跑都有可比較的結果，包含正常的漏查；不表示 Jev 獲勝。離線檢查永遠是 `audit_only`，不能代替 live 成績。初始化／查詢計時由 adapter 另列，Jev 的 trace 留存供核查；不由判斷次數推算未取得的 token 或金額。

- 已建立來源、摘要、記錄分層的題組及機械驗收；預設題組刻意包含摘要缺漏及完整記錄缺漏。
- 2026-10-01 離線實跑核對：摘要保留 4/9 項、完整記錄保留 7/9 項；兩項在完整記錄中也故意省略。這是題組的設計，不是既有小說的漏記率，也不是 Jev 成績。
- 已提供同輸入的實跑入口及離線介面測試；離線階段未啟用付費服務，以下另列使用者要求後執行的 live 結果。
- 新增的評估／adapter 離線測試為 70 項通過；全套回歸為 367 項通過、11 項略過。另核對預設 CLI、格式及文件連結；這些結果不等於真實後端的召回測量。

## 5. 同題實跑：2026-10-01

原始結果保存在 [latest-live.json](../examples/memory-eval/latest-live.json)，記錄時間為 2026-10-01 14:21（台北）。本輪只執行 `record` 組一次：9 筆相同完整章節記錄、8 題相同問題與章號限制，兩套後端全部成功，`comparison_ready=true`。沒有讀取既有小說或對話記憶，也沒有切換日常寫作後端。

請求固定為 `jev-1.13.0`，依 [TypeSafe 官方模型說明](https://docs.typesafe.ai/models)使用版本 ID，避免浮動別名；回傳報告保留請求模型名，上游 wrapper 未轉出服務實際回應模型欄位。向量模型同為已快取的 `sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2`。Chroma 1.5.9 使用隔離環境，Jev 使用原有獨立環境與 upstream commit `81574eb23f3fd8d1a6c4d54a1e7d6f2dd539e9bb`；寫作專案環境未改動。

### 延遲與採用判斷

Jev 每題外層耗時約 4.05–4.97 秒，上游 controller 回報約 0.63–1.50 秒。兩者是包含關係，不能相加。Chroma 查詢使用已載入的程序，Jev 每題重啟程序、載入 encoder 與記憶；因此表中是目前接法的延遲，不是模型或演算法單獨的速度對照。從隔離命令啟動到退出共 73.95 秒，包含環境啟動及 preflight，不含先前準備依賴的時間；首次建庫也不宜視為穩定效能。

這輪證據支持的判斷是：Jev 在一題新舊相似線索上多找回了正確來源，其他可答題與 Chroma 相同，且目前接法付出較高查詢延遲。題組只有一次、8 題，也未控制兩套環境所有向量前處理差異（例如 Chroma 環境 transformers 5.18.0，既有 Jev 環境 5.17.0）；不能據此推論所有長篇、多跳問題都優於原系統。

目前保留原後端設定。下一步優先檢查重要資訊是否被保留，再針對易混淆的長距線索評估 Jev 的增益；若要全面採用，還需檢查它是否補到完整章前包原先缺少的資訊。角色圖譜、近期記錄本來已有的內容，不能重複計為 Jev 的新增效益；本輪也沒有測試寫作 Agent 如何判讀同時召回的新舊交接記錄。

## 6. 有界 session 實跑：2026-10-01

原始結果：[latest-session-live.json](../examples/memory-eval/latest-session-live.json)。使用同一份題組、`record` 語料、模型版本與 upstream 指紋；Jev 建庫仍獨立進行，查詢改為在一次 `with JevWorkerSession()` 內共用程序及 encoder。未啟用真實小說，未讀取對話記憶，未改日常後端設定。

| 計時範圍 | 本輪結果 |
|---|---:|
| 第一題，含程序／模型冷啟動 | 4.0782 秒 |
| 後續 7 題，暖機後平均 | 0.6930 秒 |
| 後續 7 題範圍 | 0.4707–1.0995 秒 |
| 全 8 題含首次冷啟動，平均／合計 | 1.1161／8.9291 秒 |
| 查詢階段 22 次 HTTP 往返，平均 | 0.2614 秒 |
| 查詢階段單次 HTTP 範圍 | 0.1957–0.3449 秒 |

第一題 `setup_seconds` 約 2.1204 秒，包含 upstream imports 與每題元件建立；encoder 載入另占 0.7349 秒。後續每題 `encoder_reused=true`、`encoder_seconds=0`，仍重新載入圖譜（平均 0.0023 秒），並重新建立 Jev client、章號篩選及查詢引擎。沒有重用答案、被裁切的圖或 HTTP client。

HTTP 計時包住當次 SDK 的 HTTP request，含連線與讀取回應，不含 SDK 請求準備／回應驗證；不保存請求、回應內文或憑證。`api_calls`、`query_seconds`、controller 的 `latency_seconds` 及 `total_seconds` 為巢狀時間，不可加總成新的端到端耗時。外層 `elapsed_seconds` 才包含程序啟動與往返序列化；它也不是使用者從開啟命令到關閉命令的全部等待時間。

8 題兩個後端的來源章命中均與上一輪相同：Jev 仍命中 7/7 項已記錄必要證據，兩項 `capture_gap` 仍存在。Jev 查詢判斷從前輪 24 次變成 22 次：承諾題這次在 2 次即停止，前次為 4 次，其來源章相同；每題的上限仍是 4。所有已量測查詢 HTTP 均為 200；建庫另量到 17 次 HTTP，不混進查詢平均值。

前輪 8 題共 35.1015 秒，本輪共 8.9291 秒；這是兩次順序實跑，並非同時隨機對照。兩次皆重新建圖，未記錄衍生圖指紋，因此相同語料／程式版本不代表衍生圖已證明完全一致。主要可觀察差異是反覆載入已消除，但網路狀況與判斷次數也不同，不能把全部降幅歸因於模型重用。整個本輪命令 25.83 秒包含建庫、preflight 與環境啟動；Chroma 此輪建庫也比前輪快，因此不以全命令差值宣稱 Jev 加速比例。沒有量測 token 或金額，也不是一般長篇小說的效能保證。

驗收：全套離線 `428 passed, 11 skipped`；其中新增 session transport 36 項、worker/runtime 22 項與 benchmark session 3 項。另用實際 upstream mock 驗證章號截止點 `2 → 9 → 2`，排除節點 `8 → 1 → 8`，確認每題重新載入而非沿用被裁切的圖，且離開 context 後子程序已結束。單題 CLI 保持原行為；連續查詢的實際用法見[記憶流程](memory-workflow.md#同一次工作內連續查詢)。
