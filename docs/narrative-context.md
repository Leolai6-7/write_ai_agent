# 章前脈絡：事實、角色視角與作者計畫

章前包供作者維持連貫性，不代表包內每件事都已被每個角色知道。新欄位是可選的增量紀錄，舊故事不必全量補標或重建。

## 四種內容分開使用

| 分類 | 表示什麼 | 寫作時怎麼用 |
|---|---|---|
| `fact` 已確立事實 | 已在正文發生、經核對的事件或狀態 | 維持故事一致性；不能直接變成角色台詞或內心已知 |
| `knowledge` 角色已知 | 正文明確支持某角色取得的資訊 | 僅屬於指定角色；不能因別人在場或出場過就自動共享 |
| `belief` 角色信念 | 某角色相信、猜測或誤解的內容 | 保留「誰相信」及不確定性；即使和事實相反，也不可自動修成真相 |
| 作者計畫 | Beat、伏筆設計與後續安排 | 指導本章將如何發展，不當作已發生事件或角色已知 |

`characters_appeared.events`、舊 log、召回摘要及 `concepts_introduced` 保留原用途；不自動轉成上述角色知識。概念向讀者介紹過，不等於角色已經知道。沒有紀錄表示「未建立可核對的角色知情資料」，不是證明角色不知道。

## 本章視角與篇幅

卷計畫可選擇加入：

```yaml
chapters:
  - chapter: 4
    pov: 阿青
    target_length: "2,000–3,000 字"
    # 其餘既有 beat 欄位照常保留
```

`pov` 可為角色名稱字串或名稱清單，例如 `[阿青, 小嵐]`；多視角仍逐角色保留知識邊界，不合併成人人共知。未填時顯示視角未指定，不從 `characters` 的第一人或 `line` 推導。若尚未決定視角，保留未知，按本章敘事需要確認。

目標篇幅依序採用 `beat.target_length`、`planning/story_brief.md` 的「章節字數」。兩者都未提供就顯示未設定，不補一個通用字數。使用者當次指定的篇幅仍優先。

重大選擇可用 `decision_points` 交接角色的觸發、取捨與預期代價，格式及使用方式見 [重大角色決策](character-decisions.md)。非空決策計畫作為必要 `author_intent` 完整保留，仍非已發生事實或角色章前知情；未填者沿用既有 beat，不自動推造理由。這項保留只防止交接丟失，不驗證動機是否在正文成立。

## 伏筆識別與本章動作

新伏筆以穩定的 `thread_id` 串接設計、章計畫及正文後的差分，名稱只作顯示。例如在 `planning/foreshadowing.md` 使用標題 `### fs-lost-letter｜失蹤的信`，本章計畫填：

```yaml
foreshadowing:
  - thread_id: fs-lost-letter
    name: 失蹤的信
    action: plant
```

`action` 只用 `plant`（埋設）、`hint`（提示）或 `resolve`（回收）；同章可列多項動作，包括同一伏筆的埋設與回收。新格式缺動作或含無效動作會報錯，不交由工具猜測。章前包將它們標為必要的作者計畫，和歷史發生紀錄分開；只有正文實際支持時，才在章後差分記入對應動作。

圖譜差分的欄位仍是 `thread` 字串，例如 `{thread: fs-lost-letter, action: plant}`；不用改 schema。明確的 `thread_id` 按完整字串比對，不當作數字別名；更名不換 ID，也不靠顯示名稱尋找另一筆伏筆。

既有故事保留原圖譜 key、名稱及數字格式，不重編或批次遷移。舊數字、圈號與明確「伏筆 N」可按編號尋找同一舊伏筆；自由名稱則按完整名稱比對，因此「三封未寄出的信」不是「伏筆三」。舊裸名稱未列動作時，章前包會提示「動作未指定，需核對」；找不到指定設計也會明示，不能自行補成已埋設。重複或含混的識別會報錯，須先消除歧義。

## 只記重要的新增或改變

進度更新者在正文完成後，針對會影響後續行動、誤會、揭露或連貫性的重要項目填入 `narrative_updates`。不必把所有句子、動作都轉成標籤；沒有重要變化時省略整個欄位。

以下全為虛構示例。假設 `outputs/chapter_003.md` 的前三行恰為：

```text
# 第三章
阿青親眼看見阿洛把銅鑰匙放進藍盒。
門外的小嵐沒有看見這一幕，仍相信鑰匙在阿洛的口袋裡。
```

可產生：

```yaml
chapter: 3
narrative_updates:
  - id: copper-key-box-event
    kind: fact
    text: 阿洛把銅鑰匙放進藍盒。
    source: {chapter: 3, start_line: 2, end_line: 2}
  - id: aqing-key-observation
    kind: knowledge
    character: 阿青
    text: 阿青親眼見過阿洛把銅鑰匙放進藍盒。
    source: {chapter: 3, start_line: 2, end_line: 2}
  - id: xiaolan-key-location
    kind: belief
    character: 小嵐
    text: 小嵐相信鑰匙仍在阿洛口袋裡。
    source: {chapter: 3, start_line: 3, end_line: 3}
```

欄位規則：

- `id` 是穩定識別碼。同一項狀態後來改變時沿用同一 id；不要因換句話說就另造一筆。不同角色的資訊、事實與信念各用自己的 id；同一 id 不變更 `kind` 或 `character`。
- `kind` 僅允許 `fact`、`knowledge`、`belief`。後兩者必填 `character`，`fact` 不帶此欄位。計畫不可寫入此欄位。
- `text` 說清楚實際內容及其歸屬；聽到傳聞不等於傳聞成真。正文的原話、旁白與角色推測要分辨。
- `status` 預設 `active`；需要明確撤回某項信念／紀錄時，後章以同一 id 設 `retired`，並引用該章支持撤回的原文。單純未再提及，不是撤回理由。
- `source.chapter` 必須等於本份差分的 `chapter`，代表本章文本何處建立／更新這項紀錄，不是敘述中回憶事件的發生時間。`start_line`、`end_line` 是實際正文的一起算、含首尾行號；不要填示例行號或規劃文件位置。
- `source.sha256` 可在輸入省略，由 `update_graph.py` 根據該章正規化後的正文全文綁定；已提供時必須與原文相符。這不是讓作者手算 hash 的工作。

套用後，`narrative_state` 是依 baseline 與逐章差分重播的目前狀態，另有程式維護的 `introduced_in`、`updated_in`；不要直接編輯這個衍生快照。正文改稿時同步 log 與差分，再按既有 `--replace` 流程處理。

## 注入前的驗證與未知狀態

寫第 N 章時，只使用 `< N` 的歷史投影，再檢查來源正文、行段及全文 hash。原文曾變更、來源缺失或收據失效的紀錄，不作有效章前證據。

同一 id 的最新版本若已 `retired` 或來源失效，不回退舊版本把過去的信念當成現況。來源修正後，由實際覆核及差分更新恢復，不偷偷重綁 hash 來認可舊解讀。

hash 一致只表示所引用版本未改變；不代表程式已證明 `text` 的語義、角色確實知情或敘述者可靠。作者與進度更新者仍須核對原文是否支持分類及摘要。模糊推論保留為信念或未確認問題，不冒充事實。

章前包中的人物／場景活文件採有範圍的來源定位。只展開本章所需章節或行段；活文件的「當前狀態」可能包含較晚事件，不整份載入來代替歷史證據。範圍不足時做針對性補讀，保留其屬於設計、章前事實或待確認資訊的標示。

圖譜線索引用建立該項目的 baseline 或章前差分範圍，不引用含後續章節的整份圖譜。若 compact JSON 無法提供不混入相鄰資料的安全行段，就不提供整檔來源作為替代。有追蹤收據的來源章仍在 `writing` 或 `needs_review` 時，相關圖譜資訊也不當成有效證據；不要從其他入口把被排除內容補回。

## 有界上下文

`ContextBundle` 預設上限為 **12,000 個字元**。計入輸出的文字包標題、分隔與來源定位；這不是 tokenizer 計算的 token 上限，也不宣稱限制整個 JSON 回應或 Agent 後續補讀總量。

個別小說可在 `planning/context_policy.json` 設定：

```json
{"max_chars": 12000}
```

單次命令可用 `--max-context-chars` 覆蓋：

```bash
.venv/bin/python scripts/assemble_context.py --story-dir /absolute/path/to/story --chapter 4 --max-context-chars 10000 --format json
```

必要限制、本章 beat 與本章指定伏筆必須保留。明確 POV 的有效知情／信念紀錄是高優先候選，同類先取較新紀錄；不要求把人物畢生紀錄全部塞入一包。背景、近期紀錄與召回等候選也以完整條目取捨，省略清單保留定位用 ID。不能截掉「相信／尚未確認」、否定詞或來源，讓剩下的文字變成另一個意思。

寫作需要某項角色資訊但包內未列出時，先分辨它是因預算省略、來源失效、視角不符，還是本來未記錄；按省略 ID 補查必要的單項來源。不要因省略就替角色安排一次新的學習／揭露，更不能把原定後章的揭露提前當成記憶。若現有工具無法隔離安全來源，交由主 Agent 針對性補查，而不是傾印整份含未來資料的圖譜。

必要內容本身放不下時會報錯，不保存本次 context 收據，也不悄悄刪掉知識邊界。先檢查是否塞入不相關內容，再判斷是否調整本次預算；不能只為通過工具而移除必要限制。可選內容因預算未納入，不等於庫內沒有資料，按輸出的省略資訊決定是否針對性補讀。

### 省略資訊與補讀入口

JSON 的 `context_metadata` 區分 `included`／`sources`（已注入證據）與 `omitted`／`omitted_sources`（預算省略項目的 ID、原因及來源行段）；後者不含被省略的正文。`narrative_excluded` 與 `graph_excluded` 另列來源失效、視角不符或已撤回等排除原因，不把它們混成可直接使用的證據。

文字模式在文字包後附上「CONTEXT DIAGNOSTICS」導航，最多顯示 20 項、2,400 字元；**此附錄不計入 `ContextBundle.text` 的字元預算**，也不是故事正文證據。附錄顯示已列／總項數；要查看完整清單，使用 `--format json`，不靠截斷的 ID 或來源補查。沒有安全來源行段時明示缺口，不改成整檔讀取。已撤回、待覆核、來源失效或 POV 不符的內容不能因補讀而恢復成有效章前證據。

既有完成、改稿與覆核流程見 [記憶與章節工作流](memory-workflow.md)。此分層不啟用新模型、不自動補標舊故事，也不改變 Jev 的明確同步規則。
